===============================================================================
 1. FIRST CONTACT - PING FAILED, SO WHAT?
===============================================================================

First thing I did was the usual "is it alive" check:

  $ ping -c 2 -W 2 10.48.191.46

  PING 10.48.191.46 (10.48.191.46) 56(84) bytes of data.

  --- 10.48.191.46 ping statistics ---
  2 packets transmitted, 0 received, 100% packet loss, time 1022ms

A 100% loss normally means "host down", but on TryHackMe (and most cloud
networks) ICMP is very often filtered while TCP is still open. I did NOT
assume the box was dead. I re-ran the scan with -Pn, which skips host
discovery and just tries the ports.

That decision matters: if I had trusted ping, I would have walked away from a
perfectly live box.

 2. PORT SCANNING
===============================================================================

2.1 Quick targeted scan

I always start with a short list of likely ports so I get an answer fast:

  $ nmap -Pn -p 80,3389,5985 --open 10.48.191.46 -T4

  Nmap scan report for 10.48.191.46
  Host is up (0.040s latency).
  Not shown: 1 filtered tcp port (no-response)
  PORT     STATE SERVICE
  80/tcp   open  http
  3389/tcp open  ms-wbt-server

So: a web server and RDP. 5985 (WinRM) was filtered. I included 5985 on
purpose because this is a Windows box; if WinRM had been open, and I later got
credentials, I could have used evil-winrm instead of a full RDP session.

2.2 Full TCP scan

Then the full sweep, because I did not want to miss a second web port, SMB,
or some management service:

  $ nmap -Pn -p- -T4 --open 10.48.191.46 -oN ports.txt

  Nmap scan report for 10.48.191.46
  Host is up (0.048s latency).
  Not shown: 65533 filtered tcp ports (no-response)
  Some closed ports may be reported as filtered due to --defeat-rst-ratelimit
  PORT     STATE SERVICE
  80/tcp   open  http
  3389/tcp open  ms-wbt-server

  Nmap done: 1 IP address (1 host up) scanned in 163.59 seconds

Only 80 and 3389. Everything else came back filtered (no response), not
"closed". That is an important distinction. Filtered means something (a
firewall / the THM network) is dropping the packets, not that nothing is
listening. Practically it means I cannot reach SMB (445), RPC (135), NetBIOS
(139), or WinRM (5985) from here.

Assumption at this point: the intended path is web -> credentials -> RDP.
There is no SMB/MS17-010-style shortcut on this box, because 445 is not even
reachable. That is the opposite of the Blue box, where SMB was the whole game.
Different box, different story.

Lesson: a slow first connection is not the same as a dead service. Retry

3.2 The homepage

The page is a small blog called "Anthem.com". Two posts:

  - "We are hiring" (20 Jan 2020)
  - "A cheers to our IT department" (31 Dec 2019)

There is also a search box, categories, tags, and an RSS/sitemap link. The
search box is where I got my first flag, but I did not notice it yet - I read
the HTML properly afterwards.

3.3 robots.txt - the password hint

The room literally hints at "one of the pages web crawlers check for". That
is robots.txt. So:

  $ curl -s http://10.48.191.46/robots.txt

  UmbracoIsTheBest!

  # Use for all search robots
  User-agent: *

  # Define the directories not to crawl
  Disallow: /bin/
  Disallow: /config/
  Disallow: /umbraco/
  Disallow: /umbraco_client/

That first line is not valid robots.txt syntax. It is sitting above the
"User-agent: *" block, where a comment or a directive would normally be. It
reads exactly like a password, and the room hint says "possible password".
So I treated "UmbracoIsTheBest!" as a credential and kept it.

The Disallow list confirms the CMS: /umbraco/ and /umbraco_client/. So the
answers "Umbraco" and "robots.txt password" were basically free.

3.6 Flag hunting in page source

This is the part the room is really testing: read the HTML, not just the
rendered page. I used grep over the saved pages:

  $ grep -hoiE 'THM\{[^}]*\}|flag\{[^}]*\}' *.html | sort -u

  THM{AN0TH3R_M3TA}
  THM{G!T_G00D}
  THM{L0L_WH0_D15}
  THM{L0L_WH0_US3S_M3T4}

Where each one lives:

  Flag 1 - /archive/we-are-hiring/
    <meta content="THM{L0L_WH0_US3S_M3T4}" property="og:description" />
    -> It is in the Open Graph description meta tag, invisible on the page.

  Flag 2 - / (homepage)
    <input type="text" name="term"
           placeholder="Search... THM{G!T_G00D}" />
    -> Hidden in the search box placeholder text. Also appears on other pages
       because the header/search box is shared.

  Flag 3 - /authors
    Jane Doe
    Author for Anthem blog
    Website: THM{L0L_WH0_D15}
    -> This one is actually visible on the profile page, no source needed.

  Flag 4 - /archive/a-cheers-to-our-it-department/
    <meta content="THM{AN0TH3R_M3TA}" property="og:description" />
    -> Same trick as flag 1, different post.

The "meta" theme in two of the names is a hint that they are in meta tags.
The "authors" page flag is the visible one.

===============================================================================
 5. GETTING ONTO THE BOX (RDP AS SG)
===============================================================================

5.1 Credentials and why

I had a username from the poem (Solomon Grundy -> SG) and a password from
robots.txt (UmbracoIsTheBest!). The room says "The box is not on a domain",
so the login is just SG with a blank/local domain.

This is classic credential reuse: the password written in a public robots.txt
is also the Windows account password. That is the vulnerability that gets us
from "web visitor" to "interactive desktop user".

5.2 Checking the credentials without a GUI

I used FreeRDP in auth-only mode first, so I did not have to open a desktop
just to test a password:

  $ xfreerdp3 /v:10.48.191.46 /u:SG /p:'UmbracoIsTheBest!' \
      /cert:ignore +auth-only

The useful part is what it does NOT say. With the correct password there is no
LOGON_FAILURE; the client reports:

  [ERROR][com.freerdp.core] - [freerdp_connect_begin]:
      Authentication only, exit status 1

When I deliberately used a wrong password, I got the real failure:

  [ERROR][com.freerdp.core] - [nla_recv_pdu]:
      ERRCONNECT_LOGON_FAILURE [0x00020014]

So the credentials were valid. I also tried variations to be sure I was not
getting lucky with a domain format:

  SG / UmbracoIsTheBest!                    -> no LOGON_FAILURE (valid)
  .\SG / UmbracoIsTheBest!                  -> no LOGON_FAILURE (valid)
  SG / UmbracoIsTheBest! /d:WIN-LU09299160F -> no LOGON_FAILURE (valid)
  Administrator / UmbracoIsTheBest!         -> LOGON_FAILURE
  SG / umbracoisthebest!                    -> LOGON_FAILURE (case matters)

5.3 Headless RDP automation

I did not have an interactive desktop in this environment, so I drove the
session with Xvfb + xdotool and used FreeRDP's drive redirection to pull files
out:

  Xvfb :99 -screen 0 1280x800x24 &
  export DISPLAY=:99

  xfreerdp3 /v:10.48.191.46 /u:SG /p:'UmbracoIsTheBest!' \
      /cert:ignore /size:1280x800 \
      /drive:share,/home/shrdx/Documents/Anthem \
      /log-level:ERROR &

Then I opened a command prompt with Win+R -> cmd.exe and typed commands with
xdotool. The redirect shows up inside Windows as \\tsclient\share, so I could
copy files straight back to Kali.

One failed attempt worth recording: I first tried /shell:cmd.exe expecting a
console window. It just gave me the normal desktop and my typing went nowhere.
Switching to Win+R -> cmd.exe worked. Also, xdotool printed a lot of
"XGetInputFocus returned the focused window of 1" warnings on Xvfb - harmless
noise, the typing still landed.

6.2 Access denied - and why that is the puzzle

  C:\> type C:\backup\restore.txt
  Access is denied.

  C:\> dir /a /s C:\backup
  ...
  05/04/2020  22:42                21 restore.txt
                 1 File(s)             21 bytes

The file is there, it is only 21 bytes, and SG cannot read it. The room hint
is "Can we spot the admin password?" - so this is clearly the file.

I checked the ACL:

  C:\> icacls C:\backup\restore.txt
  C:\backup\restore.txt
  Successfully processed 1 files; Failed processing 0 files

Notice there are no ACEs listed at all. The DACL is empty - nobody has been
granted access, not even SG and not even Administrators explicitly. But SG
still had the ability to change the permissions, which is the flaw. The
intended GUI route is: right-click restore.txt -> Properties -> Security ->
Edit -> Add -> type "SG" -> Check Names -> give Read (or Full Control).

6.3 Granting myself read

I did the same thing from the command line:

  C:\> icacls C:\backup\restore.txt /grant %USERNAME%:R
  processed file: C:\backup\restore.txt
  Successfully processed 1 files; Failed processing 0 files.

  C:\> icacls C:\backup\restore.txt
  C:\backup\restore.txt WIN-LU09299160F\SG:(R)

  C:\> type C:\backup\restore.txt
  ChangeMeBaby1MoreTime

That is the admin password:

  Administrator : ChangeMeBaby1MoreTime

Important note: a lot of older Anthem writeups say the password is
"ChangeMe123!". On this instance it is "ChangeMeBaby1MoreTime". This is
exactly why I verified it on the live box instead of copying a writeup.

Why did SG have permission to change the ACL? Because on the file SG had
WRITE_DAC (or ownership), even though it had no read right. That is a
misconfiguration: permissions can be edited by a low-privileged user, so the
"deny" is only cosmetic. If SG had no WRITE_DAC and no ownership, this would
not have worked, and we would have needed a local privilege escalation.

6.4 Things I checked that did NOT contain the password

I did not just stop at the first promising file, so for the record:

  - C:\Users\SG\Desktop -> only desktop.ini and user.txt.
  - C:\Users\SG\Documents / Downloads / Pictures -> empty (desktop.ini).
  - C:\Users\Public -> standard folders, nothing useful.
  - findstr /s /i /m "ChangeMe" C:\Users\SG\* -> nothing.
  - C:\inetpub\wwwroot\Web\Web.config -> readable, but the Umbraco connection
    string is a local SQL Server Compact database (Umbraco.sdf); there is no
    cleartext admin password in it.
  - C:\Users\Administrator\Desktop -> as SG this returned "File Not Found"
    (i.e. no access), so root.txt was not readable as SG.

That last one confirms we genuinely needed the Administrator password; there
was no shortcut to root.txt from SG.

===============================================================================
 9. VULNERABILITIES / WEAKNESSES USED
===============================================================================

  1. Information disclosure in robots.txt
     The Windows account password "UmbracoIsTheBest!" was written in a
     publicly readable file that is specifically meant to be read by bots.
     Never put secrets in robots.txt.

  2. Secrets in page source / meta tags
     Two flags were in og:description meta tags, one in a form placeholder.
     "View source" and grep are still valid recon steps.

  3. Password reuse across the web app and the OS
     The same password protected the Umbraco site and the SG Windows account.
     One leaked password became full interactive access.

  4. Exposed RDP
     Port 3389 was reachable from the attack network with no VPN/allowlist,
     no MFA, and no account lockout issue. RDP is a very high-value target.

  5. Weak file ACL / excessive WRITE_DAC on C:\backup\restore.txt
     The file had an empty DACL, but SG could still edit its permissions and
     grant itself read. A "deny" that the user can undo is not a control.

  6. Cleartext admin password at rest
     The Administrator password was stored in plaintext in
     C:\backup\restore.txt. Backups and "restore" notes are a common place to
     find credentials.

  7. CMS fingerprinting / exposed back office
     robots.txt and the /install redirect advertised Umbraco, and /umbraco
     exposed the login page. Even without exploiting it, this gave us the
     username convention (email) and confirmed the CMS.

  8. Predictable usernames/emails from OSINT
     The "We are hiring" post gave Jane Doe and JD@anthem.com, which revealed
     the first-initial + last-initial email format. The Solomon Grundy poem
     gave the administrator's name, and the same format gave SG@anthem.com.
     Public "about the team" content is real recon material.

    answer; a longer --max-time worked. Do not call it down on one timeout.
  - Full port scan showed every port except 80 and 3389 as filtered. No SMB
    (445), no RPC (135), no NetBIOS (139), no WinRM (5985). So no
    MS17-010/EternalBlue-style route and no evil-winrm route on this box.
  - I checked 5985 on purpose because it is common on Windows; it was
    filtered, so I dropped the WinRM idea.
  - /umbraco login was not needed for the flags. It is the intended "CMS"
    confirmation, but all four flags were in public HTML.
  - C:\Users\SG\Documents, Downloads, Pictures were empty. The password was
    not hiding in the user profile.
  - findstr for "ChangeMe" across C:\Users\SG found nothing. The password was
    in C:\backup, outside the user profile.
  - Web.config had no cleartext credentials; the Umbraco DB is a local SQL CE
    file. Reading it did not hand over the admin password.
  - type C:\backup\* returned "Access is denied" because of the empty DACL.
    Reading the single file after fixing the ACL was the way in.
  - As SG, C:\Users\Administrator\Desktop was not accessible, so root.txt
    could not be grabbed before becoming Administrator.
  - /shell:cmd.exe in FreeRDP did not give me a console; the desktop loaded
    and keystrokes went nowhere. Win+R -> cmd.exe solved it.
  - RDP auth variations with the wrong domain or the Administrator account
    failed with LOGON_FAILURE, which is how I confirmed the SG login was
    actually valid rather than a client quirk.


===============================================================================
 11. WHAT I LEARNED
===============================================================================

  - Always use -Pn on CTF/lab networks. ICMP being blocked means nothing.
  - "Filtered" is not "closed". A full scan tells you which attack surface
    simply does not exist from your position. Here that ruled out SMB and
    WinRM immediately and pointed at web + RDP.
  - robots.txt is both a recon file and, far too often, a password leak.
  - Read the HTML source. Meta tags, placeholders, and comments hide flags
    and sometimes credentials. The rendered page is only half the story.
  - Blog/team content is OSINT: names, email conventions, and even poems can
    produce usernames. "Solomon Grundy" -> SG was the whole username step.
  - Password reuse is still the most reliable way from web to host.
  - On Windows, an empty DACL is not automatically safe. If a low-priv user
    has WRITE_DAC or ownership, they can grant themselves read. icacls is the
    command-line equivalent of the GUI Security tab.
  - Backup folders at the root of C: are worth checking on every Windows box.
    restore.txt was literally a plaintext admin password.
  - Verify answers against the live target. This instance's admin password is
    "ChangeMeBaby1MoreTime", not the "ChangeMe123!" in older writeups.
  - Headless RDP is very doable: Xvfb + xfreerdp + xdotool + /drive gives you
    a scriptable file-transfer channel without a real desktop.
  - Write down dead ends. Knowing that 445/5985 were filtered, that the
    Web.config had no creds, and that SG could not read the Administrator
    desktop saved time and made the successful path obvious.
